# Usertest Round 2: Dashboard Shortcuts, Less Typing for Suppliers, Shared Access

*   **Author:** Oskar Larsen
*   **Status:** Proposed
*   **Date:** 2026-11-05
*   **Related:** issue #68, branch `68-few-design-features-to-implement`, brief `concepts_brief.md`, code at `main` `b6ab1a5`
*   **Scope of this document:** the architecture covers all 25 items in the brief. The detailed implementation plan covers only the **first slice**: the invitation hijack fix, item 10 (saksnr), and group A (items 1–9 and 19). Each later group gets its detailed plan when it is built.

--------------------------------------------------------------------------------

## Overview

This design covers the changes from two rounds of user feedback on the supplier compliance app: the comments in `Usertest.comments.pdf` and a second list from 2026-11-05.

The app has two kinds of users:

*   **Admins:** municipal contract managers who follow up suppliers.
*   **Suppliers:** companies that deliver under municipal agreements and report their vehicles and certificates.

Assume neither group is good at math or at reading technical field names.

The changes fall into three themes:

1.  **Get from a number to the work behind it.** A dashboard number should open the list behind it, high risk first, with short key-word summaries and longer text one click away.
2.  **Make suppliers type less.** The app should fill in what Statens vegvesen already knows, explain fields in plain language, and let suppliers handle their own certificates.
3.  **Keep working when people are away.** Suppliers and admins should be able to bring in colleagues and stand-ins, with access that ends on its own. Admins should see who has access, and who has actually been using the app.

## The Problem

The user tests found these problems.

**Admins can see numbers but not act on them.**

*   The "High-risk suppliers" (7) and "Unresolved alerts" (20) cards can't be clicked. The suppliers page and the alerts page both have filters, but these are local page state and can't be set from a link.
*   The risk bar is one stacked line, and its high-risk part is a thin sliver.
*   The Issue categories (for example "Vehicle deviations") can't be clicked.
*   The supplier drawer gives every section the same weight. The main issue sits in the second section, and the alert is two full sentences.
*   On the Contracts page, an agreement's name is plain text. The contract status says "Expiring soon" without the date.
*   The overview export has seven metric rows. It doesn't say which suppliers or alerts are behind them, so it can't be used as a work document.

**Agreements have no case number a person recognises.** An agreement is identified by a 36-character UUID generated by the backend. Admins work with municipal case numbers (saksnr), such as `2024/1234`, which the app has no field for.

**Admins can't record or keep their own working notes.** The notes panel only works with mock data, because the backend has no notes storage. The labels don't say who a note is for.

**Suppliers type what the registry already knows and get no feedback.**

*   Suppliers type fuel type and other vehicle facts by hand, even though the backend can look a vehicle up in Statens vegvesen.
*   Field labels are technical.
*   Suppliers can't upload their own certificates.
*   Suppliers can't see any alerts about themselves, because their alerts page is a placeholder.

**Records disappear, and warnings get lost.**

*   Delete removes certificates for good. Alerts disappear from the UI after a short undo window.
*   A certificate keeps one alert row across every warning level. If an admin resolves the 90-day warning, the 30-day and expired warnings stay resolved too.
*   Miljøfyrtårn and ISO 14001 take months to renew, but the first warning comes only 90 days ahead.

**Admins can't tell whether a supplier is using the app.** When a supplier claims they made changes, the admin has no way to check. The only "last active" value in the app is the admin's own, kept in their browser.

**Only admins can bring people in, and access never ends.**

*   A supplier can't invite a colleague, and nobody can give a stand-in temporary access during holidays or sick leave.
*   The invitation code can be abused today. Creating an invitation deletes any pending invitation for the same email, even one belonging to another supplier.

## Goals

The numbers match the item numbers in `concepts_brief.md` and are stable IDs, not the build order. Items marked **[slice 1]** get a full implementation plan in this document.

**Security**

*   **G0 [slice 1].** Creating an invitation must never delete or replace a pending invitation that belongs to another supplier or role.

**A. Dashboard and navigation**

*   **G1 [slice 1].** The "High-risk suppliers" card opens the suppliers list filtered to high risk.
*   **G2 [slice 1].** The "Unresolved alerts" card opens the alerts list filtered to unresolved alerts. The number on the card equals the number of rows in the list.
*   **G3 [slice 1, admin side].** On the admin dashboard, each Issue category opens the suppliers list filtered to suppliers with that kind of problem. The supplier-dashboard side comes with G24.
*   **G4 [slice 1].** The risk bar shows one row per level: high, medium, "No flagged evidence", then "Not assessed".
*   **G5–G6 [slice 1].** An agreement's name opens its details. The status shows the date: "Expires on 31 Dec 2025".
*   **G7 [slice 1].** The supplier drawer is a short Summary: the main issue in red, then the alert titles as key words, then the follow-up status. A Details button opens a large window with the full text.
*   **G8 + G19 [slice 1].** Admins write supplier notes as either "Note to self" (only the author sees it) or "Internal note" (all admins see it). The manual-alert dialog has a "Save a note to self" checkbox. Suppliers never see notes.
*   **G9 [slice 1].** The overview export is one CSV sheet with the metrics plus the high-risk suppliers, the unresolved alerts and the deviations behind them. Excel opens it correctly with Norwegian settings.

**B. Agreements**

*   **G10 [slice 1].** Every agreement gets a saksnr, which the admin types and which is required on every save. It is easy to spot when missing. The agreement name everywhere becomes "saksnr — note".

**C. Less typing for suppliers**

*   **G11.** The supplier types the registration number. The backend fills fuel and type from Statens vegvesen when the upload is previewed.
*   **G12.** The vehicle lists show the weight range from the vehicle category.
*   **G13.** Supplier form labels are rewritten in plain language. Computed values are shown instead of asked for.
*   **G14.** Suppliers can download a CSV template and fill the vehicle form from it.

**D. Certificates**

*   **G15.** The certificate upload dialog has a searchable agreement field.
*   **G16.** Miljøfyrtårn and ISO 14001 raise a low-severity alert one year before expiry. Each warning level opens its own alert.
*   **G25.** Suppliers upload their own certificates and can renew one close to expiry. Each agreement has one live certificate per type. A supplier's renewal waits for an admin to confirm before the old certificate is archived.

**E. Keep records**

*   **G17.** Archive replaces Delete for alerts and certificates. Restore brings an item back, including its alert. Suppliers see their archived certificates in an "Archived" section.

**F. Alerts**

*   **G18.** Admins can edit the text, severity and due date of manual alerts.
*   **G24.** Suppliers get an alert feed with supplier-safe content and in-app notifications. A new manual alert and a new or escalated automatic alert both notify the supplier.

**G. Activity**

*   **G20.** Admins see "days since last active" (last check-in) and "last updated" for each supplier. "Last updated" always says whether the supplier or an admin made the change.

**H. Shared access**

*   **G21–G23.** Admins and suppliers invite colleagues themselves and can give stand-in access for up to 90 days. Stand-in access can be renewed and revoked. Admins see everyone with access and can approve, renew or remove access.

**Success check**

*   For the PDF items, the author checks each comment in `Usertest.comments.pdf` against the app by hand.
*   For every group, the acceptance checks in `concepts_brief.md` pass.

## Non-Goals

*   **Email or phone notifications.** All notices stay in the app for now. Invitation codes are passed on by hand, as today.
*   **Changing the fuel booleans to a full fuel-type model.** G11 only makes the existing fields optional.
*   **The electric-vehicle contract rules:** points, deviations for non-electric vehicles, and approval of vehicle changes.
*   **Fixing the document upload pipeline or PDF date extraction.**
*   **Storing more Statens vegvesen fields,** such as own weight, length or hybrid.
*   **Real `.xlsx` export.**
*   **Linking agreements that share a saksnr.**
*   **Limiting invitations to a company email domain.**
*   **The fuel tile in the Issue categories panel.**
*   **Detailed implementation plans for groups C–H.** This document only plans them at architecture level.

## Critical User Journeys (CUJs)

### CUJ 1: Start from the riskiest suppliers [slice 1]

*   **Given**: An admin is on the dashboard, and 7 suppliers are high risk.
*   **When**: They click the "High-risk suppliers" card.
*   **Then**:
    *   The suppliers page opens with the risk filter on High, and the URL shows `?risk=high`.
    *   The list has exactly 7 rows.
    *   Clearing the filter shows everyone, and the URL updates.

### CUJ 2: Work through unresolved alerts [slice 1]

*   **Given**: 20 alerts are open, in progress or under review.
*   **When**: The admin clicks the "Unresolved alerts" card.
*   **Then**: The alerts page opens filtered to "Unresolved" and shows 20 rows.

### CUJ 3: Read a supplier quickly, then dig in [slice 1]

*   **Given**: A supplier has 3 Euro-5 heavy vehicles that break the rules, and an active alert.
*   **When**: The admin opens the supplier, reads the Summary, then clicks Details.
*   **Then**:
    *   The Summary shows "3 Euro-5 non-compliant heavy vehicles" in red at the top, the alert title as key words, and the follow-up status.
    *   Details opens a large window in place of the panel, with the full text. Missing data shows as "Not provided yet".

### CUJ 4: Keep a private note while raising an alert [slice 1]

*   **Given**: The admin opens the manual-alert dialog for a supplier.
*   **When**: They fill in the alert, tick "Save a note to self", write the note and save.
*   **Then**:
    *   The alert is created.
    *   The note appears in that supplier's notes, marked "Note to self", for this admin only.
    *   Other admins and the supplier don't see it.

### CUJ 5: Give an agreement its saksnr [slice 1]

*   **Given**: An old agreement shows a "Saksnr missing" badge.
*   **When**: The admin clicks "Add saksnr", types `2024/1234` and saves.
*   **Then**:
    *   The agreement is named "2024/1234 — Skolerute" everywhere: on the Agreements page, in its details, in the certificate dropdown and in the export.
    *   Saving without a saksnr is refused with a plain message.
    *   Undoing an earlier change still works.

### CUJ 6: Export a work document [slice 1]

*   **Given**: The dashboard has loaded.
*   **When**: The admin clicks "Export overview report" and opens the file in Excel with Norwegian settings.
*   **Then**: The file opens as one sheet, with columns split correctly and æøå intact. It lists the metrics, then each high-risk supplier, unresolved alert and deviation, with a `Section` column saying which is which.

### CUJ 7: A supplier renews a certificate

*   **Given**: A supplier's ISO 14001 certificate has 200 days left and a low alert in their feed.
*   **When**: The supplier clicks Renew and uploads the new certificate.
*   **Then**:
    *   The supplier sees "Waiting for admin review", and the old certificate stays live.
    *   An admin sees the pending renewal and confirms it.
    *   The old certificate moves to the supplier's "Archived" section, and its alert closes.

### CUJ 8: Hand over during a holiday

*   **Given**: A supplier user is going on holiday.
*   **When**: They give a colleague stand-in access for 30 days.
*   **Then**:
    *   The colleague can work for the supplier until midnight Oslo time on the end date. After that, login is refused.
    *   The admin sees the grant in the access list and can approve, renew or remove it.

## Technical Plan (Architecture)

### System today

```text
 Browser (React + React Query)                 Ktor backend                      SQLite files
 ─────────────────────────────                 ────────────                      ────────────
 Admin pages ── apiFetch ──►  /api/admin/*  (AdminDashboardRoutes) ──► admin-insights.db (alerts, reviews)
                              /api/vehicle-fleet/* (FleetRoutes)   ──► vehicles.db (suppliers, agreements,
 Supplier pages ── apiFetch ─► /api/onboarding/* (OnboardingRoutes)        vehicles, fleet_changes, uploads)
                              /api/certificates/* (CertificateRoutes) ─► certificates.db
                              /api/auth/*  (AuthRoutes, Security.validate) ► users.db (users, invitations)
```

Some facts about today's code shape the design:

*   **Automatic alerts are rebuilt on every dashboard read.** `refreshFindings` (`AdminDashboardRoutes.kt`) derives alerts from vehicle checks and certificates, and upserts them into `admin_alerts` on each GET.
*   **No migration tool.** Each repository creates its tables with `CREATE TABLE IF NOT EXISTS`. Only `vehicles.db` has a version number (`PRAGMA user_version`, 8 or 9). The only column migration is `migrateAgreementRequirements`, and it runs only on version 8 (`VehicleDatabase.kt:28`).
*   **Request JSON is strict.** Unknown fields are rejected (`Serialization.kt:10`, and the `textFields` allowlist in `VehicleRequestJson.kt`), so the backend must deploy before the frontend whenever a request field is added.
*   **Mocks mirror the API.** Frontend API modules switch to `mocks/db.ts` when `VITE_USE_MOCKS=true`. Every API change in this design also updates the mock, so mock mode keeps working.

### Shared building blocks (used across groups)

1.  **`addColumnsIfMissing(db, table, definitions)`**
    *   One helper per database, generalised from `migrateAgreementRequirements`. It reads `PRAGMA table_info` and runs `ALTER TABLE ADD COLUMN` for each missing column.
    *   Repositories call it on **every** startup, whatever the version number.
    *   Only nullable columns, or columns with a default, are added this way. `CHECK` and `NOT NULL` constraints on existing columns are never changed.
    *   **`vehicles.db` also follows a two-release version rule,** as the brief requires:
        *   **Release 1** accepts `user_version` 10 as well as 0, 8 and 9, but changes no schema.
        *   **Release 2** adds the columns and sets `user_version = 10`.

      A rollback from release 2 to release 1 then still starts. Rolling back to any release before release 1 is not supported once version 10 is written. The other three databases have no version number and only use `addColumnsIfMissing`.
2.  **`agreementLabel(agreement)`**
    *   One frontend helper (`FE/utils/agreementLabel.ts`) and one backend function. Both return `"<saksnr> — <note>"`, or `"<saksnr>"` when the note is empty. When saksnr is missing they return `"Saksnr missing — <note>"`, or `"Saksnr missing"` with no note.
    *   Every place that builds an agreement name today uses it instead. There are about 12, using `note || id` or `` `Agreement ${id}` ``.
3.  **URL-backed filters.** The suppliers and alerts pages keep their filter state in the URL (`useSearchParams`), the same way `?supplierId` already works (`Suppliers.tsx:48-61`). A dashboard card is a plain `<Link>` to a URL with the filter set. Changing the filter on the page rewrites the URL with `replace`, and leaves other parameters such as `supplierId` alone.
4.  **Certificate-type helper** (group D)
    *   One Kotlin object normalises a type string to `MILJOFYRTARN`, `ISO_14001`, `OTHER` or `UNKNOWN`, and gives `warningDays(type)`.
    *   It is shared by items 16 and 25.
    *   The frontend's `toStandard` (`FE/api/certificates.ts:22-40`) is kept in step with it.
5.  **Alert key per warning level** (group D/E)
    *   Certificate alert keys become `certificate:<id>:<expiry>:<level>`, where level is 365, 90, 30 or expired. Each level is a new alert row.
    *   The upsert reopens a row only when the system resolved it, not an admin. That fixes lost warnings, and makes Restore bring the alert back.
6.  **Access check** (group H)
    *   One `isAccessActive(user, now)` in `UserRepository`, called by `Security.validate` and by login.
    *   It checks `access_expires_at` and walks the `granted_by` chain, stopping at the first approved or permanent account.

### Slice 1 (detailed plan in this document)

#### G0: Invitation hijack fix

`UserRepository.createSupplierInvitation` today runs `DELETE FROM supplier_invitations WHERE email = ? AND accepted_at IS NULL` for any supplier. The new rule:

*   If a pending, unexpired invitation exists for this email under a **different** supplier, refuse with `AccountConflictException` ("This email has a pending invitation from another organization"). The route already maps that exception to 409.
*   Otherwise, delete only pending invitations for the **same** supplier and email, then insert the new one.
*   An invitation older than its 48-hour expiry is treated as gone and can be replaced.

This touches one function and adds one test. No schema change.

#### G10: Saksnr

```text
 Agreement form (FleetForms.tsx)          FleetRoutes POST/PUT /api/vehicle-fleet/agreements
  [Saksnr *]  first field  ──JSON──►  AgreementInput.saksnr (required, trimmed, 1–50 chars)
  [Note]                               │
                                       ▼
                         FleetRepository.saveAgreement ──► agreements.saksnr  (TEXT, nullable)
                                                       └─► change_agreements.saksnr (history copy)
 Undo / remove ──► copy stored rows as-is (no saksnr check)
```

*   **Schema.** Add a nullable `saksnr TEXT` to `agreements` and `change_agreements` in `vehicles.db`, using `addColumnsIfMissing`, and set `user_version = 10`. This is release 2 of the version rule; release 1 shipped with G0. It also goes into `agreementColumns()` (`FleetSchema.kt:4-14`) so new databases get it.
*   **Model.**
    *   `AgreementInput.saksnr: String` is required. `FleetAgreement.saksnr: String?` is nullable, because old rows have none.
    *   `saveAgreement` checks that it is non-blank and at most 50 characters after trimming, with no format rule, so "2024/1234" is fine.
    *   Undo and remove don't go through this check.
    *   The hand-written row mappings (`FleetRepository.kt:95-101,273-278`) and the `textFields` allowlist get the new field.
*   **Read paths.** Every route that returns agreements also returns `saksnr`: the fleet overview, `AdminDashboardAgreement`, and the supplier onboarding agreement queries. The backend `primaryContract` (`AdminDashboardRoutes.kt:418`) uses the backend `agreementLabel`.
*   **Making missing saksnr easy to find.**
    *   Saksnr is the first field in the agreement form, with a label and help text: "Case number from your archive system, for example 2024/1234".
    *   On the Agreements page, an agreement without one shows a red "Saksnr missing" badge and an "Add saksnr" button that opens the form focused on the field.
    *   The page's status filter gets a "Missing saksnr" option.
*   **Naming.** UI text says "Agreement". The Contracts nav item and page title become "Agreements". Route paths such as `/admin/contracts` stay the same, so bookmarks keep working.

#### Group A: Dashboard and navigation

```text
 Dashboard                                   Target page (reads URL on load, writes URL on change)
 ─────────                                   ───────────────────────────────────────────────────
 [High-risk suppliers 7]  ── Link ──►  /admin/suppliers?risk=high
 [Unresolved alerts 20]   ── Link ──►  /admin/alerts?status=unresolved
 [Vehicle deviations 3]   ── Link ──►  /admin/suppliers?issue=vehicle
 [Certificate issues 2]   ── Link ──►  /admin/suppliers?issue=certificate
 [Risk bar row "High"]    ── Link ──►  /admin/suppliers?risk=high   (same for each row)
```

*   **G1 and G2: cards link through.**
    *   `KpiCard` gets an optional `href` and renders as a `<Link>` when it has one, like the `Metric` component (`Dashboard.tsx:317-327`).
    *   `Suppliers.tsx` sets `riskFilter` from `?risk=`, which takes `high`, `medium`, `compliant` or `unassessed`.
    *   `Alerts.tsx` gets a new status filter value, `UNRESOLVED`, meaning OPEN, IN_PROGRESS or UNDER_REVIEW, set from `?status=unresolved`.
    *   The card number and the list use the same rule: the backend's `activeAlerts` counts every non-resolved alert, so the list uses that same set.
*   **Unblocking the Alerts page.** In real mode the Alerts page fails today. It waits on `useContracts()`, which calls `/admin/contracts`, and no backend route serves that (`Alerts.tsx:38,187-195`).
    *   The Alerts page builds its "agreement" column from the fleet overview instead (`useFleet` from `hooks/useVehicles.ts`, plus `agreementLabel` on the supplier's first active agreement).
    *   The mock-only `useContracts` is removed from Alerts.
    *   `Energy.tsx` and `useRiskOutlook` also use `useContracts`. They are outside this slice and left alone, with a `shortcut:` comment.
*   **G3: Issue categories.**
    *   The backend adds `issueCategories: List<String>` to `DashboardSupplier`, holding every category that applies, not just the first. `issueCategory` stays for one release so older frontends keep working.
    *   `Suppliers.tsx` gets an issue filter, `?issue=vehicle|certificate`, which keeps suppliers whose `issueCategories` contains the matching value.
    *   `IssueCategoryPanel` tiles become links. The fuel tile stays as it is.
    *   The tile count is "distinct suppliers with that category" (`AdminDashboardRoutes.kt:476-481`), so it matches the filtered list.
*   **G4: Risk bar.**
    *   The backend adds `unassessed: RiskCount` to `RiskClassification`.
    *   Percentages use **all monitored suppliers** as the denominator, so the four rows add up to 100. Today they divide by assessed suppliers only. The existing `complianceRatePercent` KPI keeps its current denominator, so its meaning doesn't change.
    *   `RiskClassificationBar` renders four rows (dot, label, count, percent) in the order High, Medium, No flagged evidence, Not assessed. Each row is a link to the filtered suppliers list.
*   **G5 and G6: Agreement details.**
    *   `ContractDetailsDrawer` is rewritten to take `{agreement: FleetAgreement, supplier: FleetSupplier}` instead of the mock `DerivedContract`. Its layout stays, since the tester called it a good example. The file keeps its name.
    *   On the Agreements page, the agreement heading (`Contracts.tsx:101`) becomes a button that opens the drawer.
    *   The status chip shows the date:
        *   "Expired on 31 Dec 2025"
        *   "Expires on 31 Dec 2026" (both Active and Expiring soon)
        *   "Starts on 1 Mar 2026" (Upcoming)

      Dates use the existing `formatDate`.
    *   The header sentence at `Contracts.tsx:59-61` is removed.
    *   `ContractsTable`, `ContractComplianceSummary` and the `DerivedContract` paths for this page are no longer used by the page. They stay in the code, because `AlertsTable`, `EnergyTable` and `AddSupplierDialog` still import the type. Removing them is listed under Future Improvements.
*   **G7: Supplier drawer Summary and Details.**
    *   The side panel (`SupplierDetailsDrawer.tsx`) shows only:
        *   the header (name, risk badge);
        *   the **main issue** in red (`mainIssue`);
        *   **key words**: the titles of the supplier's unresolved alerts as short chips, at most 3, plus "+N more";
        *   the **follow-up status**, renamed from "Review status";
        *   the notes box (G8);
        *   a **Details** button.
    *   Details opens a large modal dialog, `SupplierDetailsDialog`, that replaces the panel: the panel closes and the dialog opens for the same supplier. Closing the dialog returns to the panel.
    *   The dialog holds:
        *   supplier information;
        *   onboarding;
        *   environmental compliance;
        *   the full alert texts;
        *   the "View submitted reporting data" button;
        *   a contracts, vehicles and certificates section, where missing data shows "Not provided yet".
    *   The "stored locally" sentence is removed, since review status is saved on the backend now.
    *   The alert chips come from the supplier's alerts in the full alert list (`GET /api/admin/alerts`, filtered by `supplierId`), not `recentAlerts`, which is capped at 10.
*   **G8 and G19: Notes.**

    ```text
     Drawer notes box: (•) Note to self  ( ) Internal note  [text]  [Save]
     Manual-alert dialog: [x] Save a note to self  [text]
              │
              ▼
     POST /api/admin/suppliers/{id}/notes  {text, visibility, alertId?}
     GET  /api/admin/suppliers/{id}/notes   → own SELF notes + all INTERNAL notes
              │
              ▼
     admin-insights.db: supplier_notes(id, supplier_id, author_id, author_name,
                                       visibility, text, alert_id, created_at)
    ```

    *   The notes live in `admin-insights.db`, next to the supplier review status, which is the same kind of admin-owned data. The `author_name` is copied in when the note is written, because user names live in `users.db`.
    *   `GET` returns the caller's own SELF notes and every INTERNAL note, newest first. No supplier route reads this table.
    *   `POST` checks that the supplier exists (through `fleet.overview()`, as the supplier-review routes do). It requires `text` to be 1–2000 characters after trimming, and `visibility` to be `SELF` or `INTERNAL`, defaulting to `SELF`.
    *   The manual-alert dialog posts the alert first. If "Save a note to self" is ticked, it then posts a SELF note with the new `alertId`. If the note fails, the alert is still kept, and the dialog shows "Alert saved, note not saved. Try again."
*   **G9: Full CSV export (built in the browser).**
    *   `DashboardExportButton` fetches the full alert list (`getAlerts()`) when clicked, then builds one sheet with these columns: `Section; Name; Agreement; Risk / Severity; Status; Category; Detail; Due date; Value`.
    *   The sections, in this order:
        *   **Metric:** the existing metrics.
        *   **High-risk supplier:** one row per supplier with `risk = high`.
        *   **Unresolved alert:** every alert that isn't resolved.
        *   **Deviation:** every unresolved alert in category `VEHICLE_COMPLIANCE`.

      A deviation is therefore also listed as an unresolved alert. The `Section` column tells the two apart.
    *   A new `toCsvSections(columns, rows)` in `FE/utils/csv.ts` writes the file:
        *   it uses one fixed column list, so rows with missing keys come out blank, not "undefined";
        *   it uses `;` as the separator and starts the file with a UTF-8 BOM, so Norwegian Excel splits the columns and keeps æøå;
        *   it keeps the existing guard against spreadsheet formulas.
    *   The existing `toCsv` stays as it is for its other callers. The risk-log export is unchanged.

### Later groups (architecture only; detailed plans come in their own documents)

*   **C (items 11–14).**
    *   During the existing upload preview (`/api/onboarding/upload/vehicles/preview`), the backend calls `VehicleRegistryLookup` for each row that has a registration number, outside the SQLite write lock, and fills in fuel and category. The preview table shows each result: filled in, "not found" (the row is blocked), or "not checked" (manual fields shown).
    *   `fuel_technology` and `is_hybrid` become optional in the CSV parser. The table columns stay, and old templates still parse.
    *   Weight range: a structured `weightRange` field on the category catalog. Labels are rewritten in plain English.
    *   A template download button and a file input use the existing endpoints.
*   **D and E (items 15–17, 25).**
    *   Certificates get `archived_at`, `archived_by`, `archived_reason`, `uploaded_by_role` and `archive_pending_for`. Alerts get `archived_at` and `archived_by`, and archiving an alert also sets `deleted = 1` so a rollback keeps hiding it.
    *   `CertificateRepository.getAll()` leaves out archived rows, and `getAllIncludingArchived()` is used for the supplier history and the admin archive view.
    *   Suppliers upload against their own active agreements, with ownership checked through `contract_id`.
    *   A supplier renewal marks the old certificate pending. Admins confirm or reject it from a queue on the Certificates page.
    *   The 365-day low alert uses the certificate-type helper and the per-level alert key.
*   **F (items 18, 24).**
    *   PATCH on alerts accepts the content fields, for manual alerts only.
    *   `admin_alerts.visible_to_supplier` is added, 0 for old rows and 1 for new ones.

*   **G (item 20).**

    *   "Last updated" is the latest of upload commits, fleet changes (with a new `fleet_changes.supplier_id`) and certificate uploads, each with the actor's role.
*   **H (items 21–23).**

    *   New `users` columns: `access_expires_at`, `granted_by`, `access_approved_by`, `access_approved_at`, `is_permanent`.
    *   Grants last at most 90 days and are capped at the granter's own end date. The `isAccessActive` chain check is used everywhere a user is loaded. There is an admin access list with Approve, Renew and Remove.

### Rollout order and compatibility

1.  **Backend first, for each step.** New request fields (`saksnr`, note `visibility`) are accepted only once the backend is deployed. The frontend for that step ships after.
2.  **Slice 1 order:**
    1.  G0, shipped together with **release 1** of the `vehicles.db` version rule, which accepts version 10.
    2.  G10: backend (**release 2**, which adds `saksnr` and sets `user_version = 10`), then frontend.
    3.  The Alerts page fix plus G1 and G2.
    4.  G3 and G4: backend fields, then frontend.
    5.  G5 and G6.
    6.  G7.
    7.  G8 and G19: notes backend, then UI.
    8.  G9.
3.  **Rollback.**
    *   Every schema change in slice 1 is an added nullable column or a new table.
    *   After G10, the backend can roll back to release 1 (G0), which accepts version 10 and ignores the `saksnr` column. Agreements saved in the meantime keep a saksnr that the older UI doesn't show.
    *   Rolling back to a build from before release 1 is not supported once version 10 is written. It would refuse to start ("Incompatible vehicle database schema").

## Alternatives Considered

Each alternative below was rejected for one of two reasons:

*   **Rejected by author:** the author decided against it in brainstorming or drafting.
*   **Rejected after review:** a Goldfish reviewer found the problem in the code and the author accepted the change.

### Slice 1

#### A1: Build the overview CSV in the backend

*   **Pros**:
    *   One place builds the file from fresh server data, in the same pattern as the risk-log export.
    *   It can be tested in `AdminDashboardRoutesTest`.
*   **Cons**:
    *   One more backend route.
    *   Frontend and backend must be deployed together.
    *   The formula-injection escaping in the frontend `toCsv` would need a backend twin, and the two must be kept equal.
*   **Reason for Rejection**: Rejected by author. The browser already has the supplier and alert data through existing endpoints, so building the file there adds no route.

#### A2: Merge the overview export into the risk log

*   **Pros**: One export button, and less code.
*   **Cons**: The two files have different readers. The risk log is an audit trail; the overview is a work document.
*   **Reason for Rejection**: Rejected by author. They stay separate.

#### A3: Real `.xlsx` export

*   **Pros**: Excel opens it correctly whatever the locale, and multiple sheets are possible.
*   **Cons**: Needs a new dependency for writing `.xlsx` files.
*   **Reason for Rejection**: Rejected by author. CSV with `;` and a BOM is enough for now.

#### A4: Show the agreement UUID as the contract number

*   **Pros**: No schema change.
*   **Cons**: A 36-character code means nothing to an admin and can't be matched against the municipality's case system.
*   **Reason for Rejection**: Rejected by author. Admins type the saksnr, and the UUID stays internal.

#### A5: A unique saksnr, or one required only when an agreement is created

*   **Pros**:
    *   A unique saksnr would catch typos.
    *   Requiring it only on create would never block editing old agreements.
*   **Cons**:
    *   One case can cover several agreements, so uniqueness is wrong for this domain. Agreements are soft-deleted and restorable by undo, so a unique index would also need a partial index and an extra undo check.
    *   Requiring it only on create would leave old agreements without a saksnr indefinitely.
*   **Reason for Rejection**: Rejected by author. Saksnr can be shared, and it is required on every save, with a "Saksnr missing" badge and filter so the old ones are easy to fix.

#### A6: Backfill saksnr on existing agreements

*   **Pros**: No "Saksnr missing" state.
*   **Cons**:
    *   There is no real saksnr to fill in.
    *   Undo compares the stored change rows with the current row (`FleetRepository.kt:202`), so changing existing rows would make every earlier change impossible to undo.
*   **Reason for Rejection**: Rejected after review. The column stays nullable, with no backfill.

#### A7: Add `saksnr` with no version bump (keep `user_version = 9`)

*   **Pros**:
    *   One release instead of two.
    *   Any older release can still open the database, because a nullable column needs no version change.
*   **Cons**: The version number no longer tells which columns a `vehicles.db` file has. That breaks the existing rule that the version describes the schema (`VehicleDatabase.kt:20-29`).
*   **Reason for Rejection**: Rejected by author. Follow the brief's two-release rule: release 1 accepts version 10, and release 2 adds `saksnr` and sets version 10.

#### A8: Summary and Details as two boxes in the same side panel

*   **Pros**: No new dialog component.
*   **Cons**: The panel stays long, and the tester asked for the long text to move out of the way.
*   **Reason for Rejection**: Rejected by author. Details opens a large window that replaces the panel.

#### A9: Rename "No flagged evidence" to "Compliant"

*   **Pros**: Shorter, and matches the tester's wording.
*   **Cons**: "Compliant" reads like an official verdict, but the app only knows that no stored check flagged anything.
*   **Reason for Rejection**: Rejected by author.

#### A10: Defer notes, or use "Note to supplier"

*   **Pros**: Deferring saves a backend table and two routes.
*   **Cons**:
    *   Notes only work with mock data today.
    *   A "Note to supplier" label promises a delivery that doesn't exist.
*   **Reason for Rejection**: Rejected by author. A small notes table is built with "Note to self" and "Internal note", and no note is ever shown to suppliers.

#### A11: "Copy to me" as an in-app notification

*   **Pros**: Matches the original wording of the feedback.
*   **Cons**:
    *   Admins already see every alert, so a copy adds nothing.
    *   It would make item 19 wait for the notifications backend (item 24).
*   **Reason for Rejection**: Rejected by author. It becomes a "Save a note to self" checkbox on the manual-alert dialog.

#### A12: One design with a full plan for all 25 items

*   **Pros**: Every file is listed once, in one place.
*   **Cons**:
    *   About 60–80 files and four database migrations would be planned in detail long before they are built.
    *   The later parts would go out of date as earlier groups change the code.
*   **Reason for Rejection**: Rejected by author. Architecture for everything, with a detailed plan for slice 1 only.

#### A13: Build strictly in group order A to H

*   **Pros**: Simple to follow.
*   **Cons**: Item 10 (saksnr) feeds the drawer, export and dropdowns in group A. Items 16–18 all change how alerts are kept.
*   **Reason for Rejection**: Rejected after review. The invitation fix comes first, then saksnr, then group A.

### Later groups (recorded here so their designs don't reopen them)

*   **Recording "last active" in `Security.validate` on every request.** Rejected after review: it puts a database write on every API call and counts idle tabs. It is written at login and `/me` only.
*   **Counting only change requests as "active".** Rejected by author: check-ins count as last active, and changes are shown separately as "last updated", with who made them.
*   **A separate access-grant table.** Rejected after review: rights are just role plus supplier today, so columns on `users` do the same job.
*   **Reusing `supplier_invitations` for admins.** Rejected after review: `supplier_id` is NOT NULL and acceptance hard-codes the supplier role, so it would need a table rebuild. A new general `invitations` table is used.
*   **An "original contact" who alone can grant access.** Rejected by author: any active user can grant. Grants last at most 90 days, are capped at the granter's end date, and admins approve the ones that should survive the granter.
*   **A new `CertificateStatus` value for the one-year warning.** Rejected after review: neither the alerts nor the frontend read that status.
*   **Removing the fuel and hybrid columns from the CSV template.** Rejected after review: every upload would fail on missing headers. They become optional.
*   **A supplier registry lookup endpoint.** Rejected by author: the lookup runs during upload preview, which avoids plate scraping and quota use.
*   **Storing weight and length from the registry.** Rejected by author: the category weight range is enough for now.
*   **Reusing the `deleted` flag to archive alerts.** Rejected by author: every alert ever deleted would become restorable.
*   **Automatic archive on supplier uploads.** Rejected by author: the expiry date comes from OCR. Supplier renewals wait for an admin to confirm.
*   **A separate Send step for alerts.** Rejected by author: creating a manual alert sends it.
*   **Email notifications now.** Rejected by author: in-app first.

## Non-Functional Requirements

*   **Security:**
    *   G0 closes a live hole: a cross-supplier invitation can be deleted and taken over.
    *   Notes are admin-only. No supplier route reads `supplier_notes`, and SELF notes are filtered by `author_id` on the server, not in the browser.
    *   The CSV export keeps the formula-injection guard.
*   **Rollout and rollback:**
    *   The backend deploys before the frontend at each step.
    *   Every schema change is an added nullable column or a new table.
    *   `vehicles.db` follows the two-release version rule, so a rollback from G10 to G0 still starts.
*   **Performance:** none of these changes is critical. The export loads every alert into the browser once per click, which is fine at a municipality's scale.
