01 Executive Summary & Core Architecture

This architectural document delivers the formal specification for onboarding suppliers onto the municipal Environmental Monitoring and Contract Compliance platform developed for Trondheim kommune (Innkjøpstjenesten). The analysis synthesizes empirical evidence obtained from inspecting every single file (42 in total) within the project's root data/ directory, cross-referenced with the existing full-stack codebase (Kotlin 2.x, Ktor, SQLite STRICT, React 19, TypeScript, Tailwind CSS).

Historically, municipal procurement follow-up relied on disparate Excel spreadsheets, scanned and redacted PDF certificates, manual warning emails (purringer), and ad-hoc communications. This platform replaces manual overhead with automated, strictly validated, and audit-proof ingestion pipelines.

Core Architectural Directive: Avoid monolithic CSVs. Data must be segregated across three natural operational vectors: (1) Contract Vehicle Fleet, (2) Facility Energy & Renewables, and (3) Supply Catalog Eco-Labels. Corporate profiles are handled via interactive web forms, while environmental management certificates are uploaded as original PDFs and extracted via native PDFBox and Tesseract OCR pipelines.

03 Project Requirements & Codebase Traceability

3.1 Requirements Backed by Existing Repository Code

  • Strict Fleet & Agreement Modeling (FleetSchema.kt, FleetModels.kt): The SQLite database enforces strict types (STRICT tables) and check constraints. The system manages suppliers (suppliers), framework agreements (agreements), authorized vehicles (vehicles), and an immutable audit log (fleet_changes) with undo capabilities.
  • Automated Statens vegvesen (SVV) Registry Verification (VehicleCheckService.kt): Vehicles submitted with a Norwegian license plate ([A-Z]{2}[1-9][0-9]{3,4}) are automatically verified against SVV. The system identifies deviations including unregistered or deregistered status, statutory driving bans (bruksforbud), propulsion mismatches (e.g. declared electric but registered diesel), and category violations.
  • Certificate OCR & Standard Identification (CertificateParser.kt, CertificateRepository.kt): Ingests PDF certificates using native PDFBox text extraction with automatic fallback to Tesseract OCR (eng+nor). Identifies standards including ISO 14001, Miljøfyrtårn, Grønt Punkt Norge, Retura, and Kurs i økonomisk kjøring. Manages expiration dates and alerts.
  • Periodic Journey & Telemetry Ingestion (trip_rows in VehicleSchema.kt): Endpoint POST /api/trip-rows receives batched operational trip records (distance, fuel consumption, NOx, CO2) for post-onboarding performance tracking.

3.2 Implementation Gaps Identified

  • Supplier Workspace Tenant Scoping: In frontend/src/pages/supplier/ (e.g. MyVehicles.tsx, MyCertificates.tsx), views are mock prototypes flagged with {/* TODO: scope all data to the authenticated supplier's own organization only */}.
  • Persistence for Facility Energy: The frontend prototypes an energy dashboard (/admin/energy), and sample submissions exist in data/, but there is no SQLite table to persist facility area and energy consumption.
  • Product Eco-Label Catalog: Procurement tenders mandate tracking eco-labeled goods (Svanemerket, Möbelfakta), but no relational schema exists for contract product lines.
  • Two-Phase CSV Upload Pipeline: The backend supports single-item JSON creation but lacks an atomic, batched CSV ingestion pipeline with dry-run preview and commit semantics.

05 Detailed CSV Ingestion Specifications

Global Ingestion Rules: CSV uploads accept comma or semicolon delimiters; downloaded templates use semicolons for compatibility with Excel in comma-decimal locales. Use UTF-8 with BOM encoding, ISO 8601 dates and weeks, period decimal points (.), uppercase booleans (TRUE / FALSE), and empty fields for nulls. To prevent CSV Formula Injection (CWE-1236), values starting with =, +, -, @, \t, or \r are strictly rejected by the parser.

07 Backend Architecture & Ingestion Lifecycle

7.1 Onboarding State Machine

[INVITED] ──> [PROFILE_PENDING] ──> [DATA_DRAFT] ──> [VALIDATING] ──> [SUBMITTED]
                                         ^                 │               │
                                         │ (Correction)    │ (Errors)      │
                                         └─────────────────┴───────────────┤
                                                                           v
                                                                   [UNDER_REVIEW]
                                                                    │          │
                                                    (Approved)      │          │ (Changes Req.)
                                                                    v          v
                                                               [APPROVED]  [REVISION_REQUIRED]

7.2 Ingestion Policy: Atomic All-or-Nothing vs. Partial Commits

Architectural Decision: Strict All-or-Nothing Atomic Ingestion.
Partial row imports are rejected. Transport contracts have strict quotas (allowed_vehicles). If 8 out of 10 rows succeed, the supplier often re-uploads the whole spreadsheet, causing duplicate collisions or silent gaps in route coverage. Instead, the Two-Phase Preview & Commit pattern is enforced:
  • POST /api/onboarding/upload/{entity}/preview parses all rows, validates SVV checks, and returns a detailed diff showing every invalid cell without committing to the database.
  • POST /api/onboarding/upload/{entity}/confirm commits the verified payload in a single atomic database transaction once 100% of rows are valid.

7.3 Production SQLite DDL Migrations

-- 1. Onboarding Status Tracking Table
CREATE TABLE IF NOT EXISTS supplier_onboarding (
    supplier_id TEXT PRIMARY KEY REFERENCES suppliers(id),
    status TEXT NOT NULL CHECK (status IN (
        'INVITED', 'PROFILE_PENDING', 'DATA_DRAFT',
        'VALIDATING', 'SUBMITTED', 'UNDER_REVIEW',
        'APPROVED', 'REVISION_REQUIRED'
    )),
    contact_name TEXT,
    contact_email TEXT,
    contact_phone TEXT,
    submitted_at TEXT CHECK (submitted_at IS NULL OR (julianday(submitted_at) IS NOT NULL AND substr(submitted_at, -1) = 'Z')),
    reviewed_at TEXT CHECK (reviewed_at IS NULL OR (julianday(reviewed_at) IS NOT NULL AND substr(reviewed_at, -1) = 'Z')),
    reviewer_notes TEXT,
    updated_at TEXT NOT NULL
) STRICT;

-- 2. Audit Trail for Batch Uploads
CREATE TABLE IF NOT EXISTS upload_batches (
    id TEXT PRIMARY KEY,
    supplier_id TEXT NOT NULL REFERENCES suppliers(id),
    agreement_id TEXT REFERENCES agreements(id),
    entity_type TEXT NOT NULL CHECK (entity_type IN ('VEHICLES', 'ENERGY', 'PRODUCTS')),
    file_name TEXT NOT NULL,
    file_hash_sha256 TEXT NOT NULL,
    total_rows INTEGER NOT NULL CHECK (total_rows >= 0),
    valid_rows INTEGER NOT NULL CHECK (valid_rows >= 0),
    error_rows INTEGER NOT NULL CHECK (error_rows >= 0),
    status TEXT NOT NULL CHECK (status IN ('PREVIEWED', 'COMMITTED', 'DISCARDED')),
    created_at TEXT NOT NULL,
    committed_at TEXT
) STRICT;

08 Security, GDPR & Risk Mitigation

Risk Domain Identified Threat / Vulnerability Impact Architectural Mitigation Strategy
GDPR & Personal Data Driver names, phone numbers, or private license plates exposed in public audits. Medium (GDPR / Norwegian Privacy Law) Do not request driver identities in fleet CSVs. Treat vehicle plates strictly as operational contract assets. Mask sensitive contact data in administrative exports.
SVV API Rate Limiting High-volume batch vehicle uploads exhausting the Statens vegvesen Enkeltoppslag quota. High (System Outage) Utilize the existing 14-day cached registry snapshot architecture (svv_snapshots). Run batch lookups through a rate-limited asynchronous worker queue.
Tenant Isolation Breach Malicious supplier crafting CSV payloads referencing another supplier's agreement_id. Critical (Data Tampering) Derive supplierId strictly from the verified JWT session cookie. Enforce server-side ownership checks on all referenced agreements before parsing rows.
CSV Formula Injection Spreadsheet cells containing =CMD(), +DDE(), or malicious macro triggers. High (Client Compromise) Sanitize all free-text fields. Reject or escape cells starting with =, +, -, @, \t, or \r.
